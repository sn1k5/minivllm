## 1. 项目介绍话术（三档）

**30 秒版**：
从零实现的 LLM 推理引擎，不依赖 vLLM，覆盖调度、显存管理、投机解码、量化、服务化全链路。
核心特色是"每个优化都有实测数据"：fa2 + Decode CUDA Graph 下并发 16 吞吐 3794 tok/s
（单 token 延迟 2.9ms，并发 1→16 ITL 几乎不变）；前缀缓存命中 74% 时 TTFT 降 31%；
n-gram 投机解码 eager 模式加速 3.5 倍（并实测了 CG 下变负收益的边界条件）；
W8A16 量化权重显存 -29%。所有开关可参数化，bench 脚本一键复现。

**2 分钟版**：在 30 秒版基础上展开三条主线——
1. **显存这条线**：PagedAttention 分页 + hash/radix 前缀索引 + 链哈希主机留档的
   多级 offload（淘汰留档、命中异步拉回）+ swap/recompute 双模式抢占（成本模型自动选）；
2. **调度这条线**：chunked prefill 与 decode 混跑、SLO 优先级、自适应 token 预算、
   保守准入，四个策略全部有开关和对照数据；
3. **算子与量化这条线**：FlashAttention/torch SDPA 双注意力后端、FlashInfer 小算子、
   自研 Triton dequant GEMM 的 W8A16、FP8 KV cache（写入核内量化 + 页表反量化）。
最后落到工程化：OpenAI 兼容 API（流式 + tool calling）、缓存感知多实例路由、
自实现 Prometheus 指标，形成"优化 → 指标 → 验证"闭环。

**5 分钟版**：在 2 分钟版基础上，挑 2 个模块讲设计取舍（推荐：offload 的同步写/异步读
权衡 + 投机解码的页管理联动），并主动交代已知限制（见第 13 节）——面试官最看重
"知道自己系统边界"的候选人。

## 2. 整体架构

三面分离，职责边界清晰（面试官问"模块怎么划分"直接答这个）：

```
Engine（门面：tokenizer、编码校验、流式）
  └─ Client（dp=1 Inproc / dp>1 MPClient via ZMQ）
       └─ EngineCore（核心循环：schedule → run → read_samples → update）
            ├─ Scheduler        控制面：四队列 + 页预算 + 策略
            ├─ KVManager        控制面：页账本 + 前缀索引 + offload 账本
            └─ Executor         执行桥
                 ├─ UniprocExecutor（tp=pp=1，同进程直调）
                 └─ MultiprocExecutor（Gloo 广播调度 + NCCL 计算面）
                      └─ Worker / ModelRunner（计算面）
                           ├─ Batch（静态缓冲 + pinned H2D）
                           ├─ KVPool（[2, L, B, bs, nkv, hd] 单池）
                           ├─ layers（attention 后端 / linear / rmsnorm / rope）
                           └─ models（qwen3 / qwen3_moe）
```

**关键设计决策（容易被追问）**：
- **控制面不 import torch**（KVManager/BlockManager 纯 Python）→ 调度器逻辑可用
  CPU 单测直接验证（`tests/unit/test_scheduler_cpu.py` 用真实 KVManager 跑通
  优先级/准入/抢占/投机全场景）；代价：offload 的页拷贝必须限定在单进程执行器。
- **页号账本（data/）与页存储（compute/kv_pool）分离**：账本只有整数页号，
  存储是 GPU 张量；两者通过 block_table 对齐。
- **wire 协议（msgspec）**：ScheduledBatch.to_wire 只发增量字段（token 切片、块表引用），
  不发全量历史——跨进程广播量最小化。

## 3. KV 管理与 PagedAttention

**三态页池**（BlockManager）：free / used（ref_count≥1）/ cached（已发布前缀、ref=0）。
缺页时腾位顺序：radix 冷叶回收（reclaim_fn）→ LRU 驱逐最旧 cached 页。

**链哈希**：block i 的哈希 = H(block_i 的 tokens, hash_{i-1})，首块 prev=-1。
- 命中匹配 O(1)/块且天然携带前缀身份——后续 offload 的主机索引直接复用它，
  无需第二棵树。
- 发布（publish）：写满一块登记哈希 + token_ids；驱逐（invalidate）摘索引。

**为什么只有 K/V 能缓存**（高频问答）：一次前向的中间量分三类——参数（不变）、
逐 token 中间量（每步变）、逐位置量（内容有效且被重复引用）。只有第三类满足缓存
两条件：内容在后续计算中不变 + 被后续步骤反复读取。K/V 恰好属于第三类；
hidden state 只被下一步消费一次，不满足"重复引用"。

**PagedAttention 解决什么**（高频）：朴素预分配连续 KV 缓冲 → 内部碎片（短请求
浪费预留）+ 外部碎片（并发下无连续大块可分配）。分页 = 虚拟内存思路：逻辑块表
（连续）→ 物理页（离散），显存利用率接近 100%，且为前缀共享和 offload 提供了
页粒度操作的基础。

**block_size=256 的取舍**：FA2 paged kernel 要求 256 倍数；页越大单页元数据开销越小，
但碎片与抢占粒度越粗。追问"为什么不 16/32"：FA2 约束 + 我们的 offload/前缀发布
都以满块为单位，大块让满块率更高。

## 4. 调度器（四队列 + 五策略）

**四队列**：waiting（FCFS/优先级）→ running（decode 每步全员推进）→
swapped（整序列换出待换回）→ restoring（异步拉回中，不占调度名额）。

**主循环**：`schedule()` 先轮询 restoring/尝试 swap-in，再按 mixed（decode 优先 +
剩余预算给 prefill chunk）或 prefill-first 产出 ScheduledBatch；`update()` 回填
token、sync_prefix、判结束回收。

**五策略**（全部配置开关，均实测）：
| 策略 | 机制 | 实测 |
| --- | --- | --- |
| A1 抢占双模式 | recompute 释放重算；swap 整序列换出主机。auto 模式按
已算 KV 量（num_cached_tokens ≥ 阈值）选 swap | swap 吞吐 +15%，ITL P99 268ms vs 45ms |
| A2 SLO 优先级 | priority 大者优先出队；deadline 临近自动提权；decode 侧不动
（每步全员推进保 ITL 公平） | 单测覆盖 |
| A3 自适应预算 | prefill budget = base×(1−α×decode压力)，EMA 平滑，
decode 配额不受影响 | 单测覆盖 |
| A4 保守准入 | 放行前预估 (prompt+生成估计)/块大小 的整生命周期需求 | 抢占 2→1 |
| D1 投机解码 | 见第 6 节 | 3.3x |

**踩坑与修复（面试可讲的真实故事）**：
1. swap 换入门槛只看 free blocks，导致 swapped 序列饿死死锁——修复：计入可驱逐的
   cached 块（swap_in 内部会先驱逐已发布前缀）。
2. 异步拉回在途时，idle 守卫空转 1024 步（纯 Python，<0.5s）误判死锁——修复：
   restoring/swapped 非空时视为"正常等待"不计空闲。
3. 遗留问题：3 并发+极小池的抢占风暴可能进入 recompute 活锁（抢占→重算→再抢占），
   需要"抢占预算/分批重准入"，在 ROADMAP。
→ 讲这些的信号：我知道自己系统在什么负载下会翻车，并且知道为什么。

## 5. KV offloading（HBM → 主机内存）

**三个角色**：账本（data/offload.py，纯 Python：槽位/链哈希索引/LRU/任务登记）、
主机池（compute/offload.py，pinned 内存 + 独立 CUDA stream + Event）、
淘汰挂钩（BlockManager 淘汰前调 preserve）。

**数据流**：
1. 留档：cached 页被淘汰前 `preserve(bid, hash)` —— **同步** D2H（调度期计算流空闲，
   单块 0.5~2ms），失败照常丢弃；
2. 命中：allocate 在 GPU 命中断点后用链哈希查主机索引 → 分配新 GPU 页 →
   **异步** H2D（pinned 源 + 独立 stream + Event）；
3. 等待：序列进 restoring 队列，不占 waiting/running 名额；每轮 schedule 先
   poll_restore，Event 就绪才回 waiting——拉回期间其他序列照常跑；
4. 主机满：LRU 挤掉最久未用的留档页。

**核心权衡（必被追问）**：为什么写同步、读异步？——写入侧发生在调度路径上，
若异步则"页已归还但拷贝未完成"存在竞态（页被复写）；读取侧（拉回）不阻塞任何
队列，异步收益最大且无竞态（页在拉回完成前不会被前向触碰，Event 就绪才调度）。

**实测**：小池压力下吞吐 +9~11%，留档 7 块、二次访问主机命中 2 次、拉回 5 块。

## 6. 投机解码（n-gram）

**提案**：维护"上下文元组 → 后续 token 列表"（窗口 n=3）；prompt 首次全量建表，
验证后增量喂入；贪心链式提案（命中后上下文滑动继续查），最多 K=4 个。

**验证**：q = [最后 token] + 草稿，走 prefill 变长通路一次前向——所有 q 位置的
argmax 与草稿逐位比对，取最长接受前缀；提交 accepted+1 个 token；
**页管理联动**：调度期按 1+K 预分配页（may_append_for），验证后 shrink 回收
被拒草稿的页（尾部页 ref=1 且未发布才回收，防御共享块）。

**限制与原因**：仅支持 greedy（temperature=0）。验证本质是 target argmax 与草稿
比对；采样场景需要 rejection sampling（按 target 分布接受/拒绝并修正残差分布），
在 ROADMAP。CUDA Graph：投机步绕过 CG（走变长通路），无草稿步仍走 CG。

**实测**：重复模式负载 32→94 tok/s（3.3x），接受率 100%（理想负载，诚实声明）。

## 7. 量化

**W8A16（在线 quantize-on-load）**：
- per-output-channel absmax：scale=amax/127，q=round(w/scale)，clamp [-127,127]；
- 权重加载时逐层完成（weight_loader 内"先量化整张、再按 TP 切片"），无需离线校准；
- 前向：Triton dequant GEMM——int8 tile 转 fp 后乘 per-row scale 再 tl.dot，fp32 累加；
- 范围：四类投影层（Column/Row/Merged/QKV）量化；Router gate 与 lm_head 不量化
 （精度敏感）；MoE 专家暂不量化。

**实测解读（必被追问"为什么吞吐反而降 14%"）**：0.6B 小模型 decode 受权重带宽限制，
int8 理论省一半带宽，但朴素 dequant GEMM（固定 64×64×64 tile、未 autotune）的
额外反量化开销超过带宽收益；且权重显存 -29% 而非 -50%（embedding/lm_head/norm
保持 FP16）。改进路径：autotune + 更大模型（带宽瓶颈占比更高）→ 4090 补测。
质量：自然语言 prompt 贪心输出重合率 89.8%。

**KV FP8**：写入核内完成量化（以该 token 的 K 向量 amax 定 per-token scale，
K/V 共用同一 scale，scale 落表）；读取按页表 gather 反量化后走 varlen attention。
限制：sm_86 的 Triton 不支持 fp8e4nv 存储类型（需 sm_89+），3080 Ti 无法实测，
4090 补测。

## 8. 注意力后端

**fa2 路径**（flash_attn）：prefill 走 varlen + block_table（paged），decode 走
flash_attn_with_kvcache；支持 CUDA Graph。
**torch SDPA 兜底路径**：页池按页表 gather 成 padded batch（Triton kernel，
256 对齐缓冲复用）→ SDPA(enable_gqa) + bool mask；纯 torch，任何环境可跑，
eager only。

**两个可以讲的调试故事**：
1. **flashinfer 0.6.13 上游 bug**：其 paged attention wrapper 在本机
   （cu130 + sm86）对 num_kv_heads>1 输出错误——fa2/triton/cutlass/trtllm_gen
   四种后端一致复现同一错误值，说明是共享的输入预处理问题；逐头比对定位到
   GQA 分组路径，确认上游问题后放弃用其做注意力，只保留已验证正确的小算子
   （rmsnorm/silu/rope）。方法论：先复现→变量隔离→逐头比对→多后端交叉验证。
2. **fa2 ABI 排查**：torch 2.14.1 下 flash_attn cu130+torch2.13 wheel 报
   undefined symbol（C++ ABI 变更）；查 mjun0812 releases 发现 torch2.14 只有
   Windows wheel、Linux 最新只到 torch2.15——最终把 torch 降到 PyPI 官方的
   2.13.0（恰好捆绑 cu130），与 README 标准栈对齐后 fa2 正常。方法论：
   符号名解码 → 确认构建 torch 版本 → 全量盘点上游 wheel 矩阵 → 版本对齐。

**数值验证方法**（体现严谨性）：小规模页池 + 已知输入，对照 fp32 手工
softmax(QK^T/√d)V 逐头比对，decode/prefill 误差 ≤5e-4。

## 9. 服务化

- **AsyncEngine**：后台线程跑 engine.step() 死循环，每步 diff 各请求 completion
  token 增量，经 loop.call_soon_threadsafe 推给每请求独立的 asyncio.Queue——
  请求间无交错；stop strings 在文本层检测命中即截断。
- **tool calling**：hermes 风格 `<tool_call>{json}</tool_call>` 流式解析——状态机
  + 括号深度扫描（跟踪 in_string/转义），增量发 args delta；非流式聚合为
  OpenAI tool_calls 格式。
- **缓存感知路由**：打分 = w1×前缀命中比（各实例 /internal/prefix_probe 只读探测，
  不分配页）+ w2×(1−队列深度) + w3×(1−KV 水位)，乘实例权重取 argmax；失败实例跳过。
- **Prometheus**：自实现 Counter/Gauge/Histogram + 文本渲染，零第三方依赖；
  覆盖 TTFT/ITL/queue time/KV 利用率/前缀命中率/投机接受率/抢占与 offload 计数——
  上面所有优化都用这套指标对照验证。

## 11. 高频面试题与答案要点

**显存与 KV 管理**
1. PagedAttention 为什么能提升显存利用率？——消除内部/外部碎片；朴素预留按最大输出，实际平均利用率低，分页后接近满用。
2. 前缀缓存怎么判断命中？——链哈希逐块比对（哈希 + token_ids 双重校验防碰撞），radix 树支持任意公共前缀长度。
3. 块什么时候会被驱逐？——ref=0 进入 cached（LRU）；radix 下优先摘冷叶；used 块（被活序列引用）不可驱逐。
4. KV cache 能不能缓存 hidden states？——不能：内容有效 + 被重复引用两个条件只有 K/V 满足。

**调度**
5. chunked prefill 解决什么？——长 prompt 一次性 prefill 阻塞同批 decode 的 ITL；切块混跑摊到多步。为什么 decode 优先？——decode 每 seq 只占 1 token，优先调度成本极低且保住 ITL。
6. 抢占时 recompute vs swap 怎么选？——按已算 KV 量：算得多 swap，算得少 recompute；auto 阈值 512 tokens。
7. 准入控制为什么能减少抢占？——抢占根源是"准入时的乐观估计"，保守准入按整生命周期预留，宁可晚进不抢占。
8. 优先级调度为什么只动 prefill 不动 decode？——decode 每步全员推进已公平；TTFT 才是优先级敏感指标。
9. 自适应预算的反馈信号？——decode 队列压力（即时指标），EMA 平滑防抖；不用 ITL（滞后指标）。

**投机解码**
10. 为什么 n-gram 不需要训练？——draft 分布来自序列自身历史统计而非模型。
11. 验证时 KV 怎么处理？——K+1 个 query 位置的 KV 全写入页池，接受前缀保留，被拒草稿页 shrink 回收（尾部页未发布无共享，可安全回收）。
12. 为什么只支持 greedy？——greedy 验证 = argmax 比对；采样需 rejection sampling + 残差分布重采样（ROADMAP）。
13. 投机解码什么时候反而变慢？——接受率低时：草稿位前向 + 页管理开销 > 省下的 decode 步数；K 按滚动 accept rate 调。

**量化**
14. W8A16 为什么不用 GPTQ/AWQ？——absmax per-channel 无需校准、加载即用，是精度/复杂度第一台阶；GPTQ 校准是第二台阶（ROADMAP）。
15. per-channel vs per-tensor？——per-channel 对 outlier 友好；TP 下 scale 随行切分，数学一致。
16. 为什么 Router/lm_head 不量化？——router 决定离散路由、lm_head 决定 argmax，精度极敏感且显存占比小。
17. FP8 KV 的 scale 粒度？——per-token（写入时按 K 向量 amax 定标，K/V 共用）；无需校准且自适应分布。

**注意力与算子**
18. GQA 实现要点？——SDPA enable_gqa / FA2 原生分组；自研路径的坑：bool mask 语义（True=参与）与 batch 维展开。
19. 为什么 FlashInfer 只用小算子？——本机实测其 paged wrapper 对 h_kv>1 输出错误（四后端一致复现，上游问题）；讲排查方法论（第 8 节）。
20. torch 后端为什么慢？——每步每层 gather（额外 KV 读写）+ padded SDPA；fa2 直接页池 paged 读取。

**服务化与工程**
21. 流式输出怎么隔离请求？——每请求独立 asyncio.Queue + 工作线程 call_soon_threadsafe 投递。
22. 路由器前缀探测为何无副作用？——只调 index.match 只读路径，不分配页不 pin 节点。
23. 为什么自实现 Prometheus？——依赖极简 + 格式简单，约 100 行可控。
24. dp/tp/pp 分叉点？——dp 在 Engine 副本层（MPClient/ZMQ），tp/pp 在 Executor 广播层（Gloo 控制面 + NCCL 计算面）。
25. offload 为什么只支持单进程执行器？——页号账本在控制面、页拷贝在计算面，跨进程需 RPC 化拷贝后端（ROADMAP）。

## 12. 与 vLLM 的对比（被问"和 vLLM 差在哪"时）

| 维度 | minivllm | vLLM |
| --- | --- | --- |

## 13. 已知限制（诚实清单，主动交代）

1. offload/swap 仅单进程执行器（tp=pp=1）；多进程需 RPC 化拷贝后端。
2. torch 注意力后端仅 eager（CG 下自动切换 fa2）；投机验证步绕过 CG——
   CG 下投机为负收益（已实测），需 piecewise CUDA Graph 解决。
3. flashinfer 0.6.13 attention 在本机环境 h_kv>1 错误（上游），仅用其小算子。
4. 投机解码仅 greedy；采样需 rejection sampling。
5. W8A16 未 autotune，小模型上吞吐负收益（-14%）。
6. AsyncEngine 增量解码为全量 decode+diff（长输出 O(n²)）。
7. MoE 专家权重未量化。
8. 极端抢占风暴下 recompute 活锁（需抢占预算策略）。
9. KV FP8 未实测（sm86 硬件限制）。

## 14. 后续规划（"接下来做什么"的标准答案）

**A. 4090 补测清单（硬件到位即可跑，零新代码）**
- KV FP8：显存减半 + 可服务并发 + 质量重合率（sm89 支持 fp8 Triton）。
- vLLM 同机对拍：`bench/vs_vllm.py` 骨架已就绪。
- fa2 + CG 的吞吐数据已在 3080Ti 完成（见第 16 节），4090 上复测大模型档位。

**B. 调度与显存（1~2 天/项）**
- 抢占预算/分批重准入：修复极端抢占风暴下的 recompute 活锁。
- NVMe 三级 KV 存储（LMCache 风格）：主机内存二级、SSD 三级。
- 淘汰策略升级：LRU → 命中频次加权（LFU/ARC），用 preemption/host_hits 指标对照。

**C. 投机解码升级（3~5 天）**
- 小模型 draft（0.6B draft → 1.7B target）+ FlashInfer spec decode 接口。
- 采样场景 rejection sampling；自适应 K（按滚动 accept rate 调整草稿数）。

**D. 量化深化（4~5 天）**
- W8A16 Triton kernel autotune；MoE 专家 groupwise 量化；W4A16（AWQ）。

**E. 服务化增强（各 1~3 天）**
- 结构化输出（logits mask 约束解码）；请求取消/超时传播到调度器；
- 在线学习路由（ε-greedy 多臂老虎机）；跨实例前缀元数据同步。

**F. 分布式方向（1~2 周，需多卡环境）**
- PD 分离：prefill/decode 分实例 + KV 传输协议（单机双进程模拟）。
- 分布式 KV pool：账本中心化 + RPC 拷贝后端（复用 HostKVBackend）。
